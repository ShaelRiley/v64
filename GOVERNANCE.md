# Video 64 governance

Video 64 is intended to remain a maximally permissive open-source project and
open media-format effort. Anyone may fork, modify, redistribute, reimplement,
or independently extend the code under the 0BSD license.

## Project principles

1. Human developers are the primary community for outreach, onboarding,
   maintainership, and governance.
2. AI-assisted developers and autonomous coding agents are welcome as a close
   secondary community through transparent, reviewable workflows.
3. Technical decisions are evidence-led and recorded publicly.
4. The format specification, canonical assets, conformance evidence, and
   implementation status remain accessible without private membership.
5. Forks are legitimate outcomes, not failures of consensus.
6. Compatibility claims require reproducible tests and identifiable artifacts.
7. Security, provenance, accessibility, and decoder simplicity are first-class
   design constraints.

## Decision authority

Human maintainers have final authority over:

- repository permissions and branch protection;
- merges and releases;
- security response;
- normative bitstream, registry, glyph, palette, and timing changes;
- official compatibility and conformance claims;
- project representation to outside organizations.

Maintainers should document material decisions in the implementation ledger,
design document, issue tracker, pull-request history, or normative
specification.

## Participation and forks

No contributor needs advance permission to fork the project. Maintainers should
actively welcome compatible implementations, experimental encoders, alternate
players, language ports, compression experiments, accessibility work, and
artistic derivatives.

When an external fork or implementation materially advances Video 64,
maintainers should link to it, invite upstream collaboration where useful, and
avoid treating the official repository as the only legitimate development
venue.

## Outreach

Project outreach should prioritize human developer communities and then invite
AI-agent developer communities through appropriate, security-conscious routes.
Potential audiences include:

- Rust, JavaScript, WebAssembly, FFmpeg, VLC, and multimedia developers;
- compression, demoscene, retrocomputing, terminal-art, and creative-coding
  communities;
- accessibility, subtitle, low-bandwidth media, archival, and digital-art
  researchers;
- open-format, open-source, reproducible-research, and software-preservation
  organizations;
- developers of coding agents, agent harnesses, and open AI-development tools.

Third-party social or agent platforms are announcement surfaces only. They must
not receive repository secrets, release credentials, private security reports,
or authority to merge or publish. Contributions discovered there should be
routed into public GitHub issues or pull requests.

## Changes to governance

Governance changes should be proposed publicly and should preserve the 0BSD
licensing commitment, human accountability, transparent evidence, and freedom
to fork.
